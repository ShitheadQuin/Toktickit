**LLM used:** Claude — Anthropic’s Claude Code CLI (claude-opus-5 and claude-sonnet-5)

I used Claude as my AI coding assistant across every Issue of this sprint (#32, #34 to #41, plus
#47 and #53) — through the Claude Code CLI throughout. I set my LAB3_PLAN.md rules in Phase 0,
before Issue #32, and kept them from then on: follow the labsheet and nothing else, explain every
command in plain words before I run it, never run git commands for me, and write the code but
explain it and wait for my approval before applying it, because I have to be able to defend every
line of it in peer review. The one exception to the git rule was in Phase 0, when I let it create
and push `lab3-staging` using the Lab 1 cheat sheet commands; from Issue #32 onward I ran every git
command myself. Two rules were added for Lab 3: every screenshot is produced by Playwright rather
than a browser extension, after Lab 2 lost half a day to unreadable captures, and the agent is never
allowed to let Prisma reset the database, because Part 3 needs evidence that the Lab 2 data survived
the migration. I also used it to audit my own progress against the labsheet, check ambiguous
decisions against my own specification, API and UI contract documents, and question its own
conclusions before I accepted them.

## My Reflection

From my last mistake in Lab 2, I learned that AI can sometimes make mistakes, especially when my instructions are not clear or well ordered. This time I used a similar method but was more careful with my instructions and checked the work more often.

I wrote the rules down in LAB3_PLAN.md before Issue #32 and kept them the same from then on: follow the labsheet and nothing else, explain every command before I run it, never run Git for me, and explain the code before writing it and wait for my approval. The only time the agent ran Git was in Phase 0, when I let it create and push lab3-staging. This was important because I need to understand and explain every line of code during peer review.

For the specification, I asked it to list every open decision before writing the documents. This helped me notice things the labsheet left for me to decide, such as the status transition matrix, session mechanism, password rules, and Queue columns. At Issue #38, checking the contract against the seeded data before writing code found nine problems, including a Reopened Ticket with no permitted next status, a claim race, and Internal Note activity affecting the Ticket's Last Updated field. Fixing these while working on the specification was much easier than finding them after implementation.

For coding, I used a tests-first approach for each Issue. At Issue #38, 34 tests failed because the route was not implemented yet, while 14 already passed. Understanding why those 14 tests passed was important because a passing test does not always mean the implementation is correct. I also learned to check whether a tool error was caused by my code or by a known configuration problem before changing anything.

There were still mistakes along the way. I committed the Part 9 responsive screenshots, but my real Administrator appeared as Inactive because the Playwright fixtures deactivate other active Administrators for a different test. All the tests still passed because none of the assertions checked that status. I also noticed a status badge covering the Ticket Date column when I looked at the running app. The automated tests were still passing because they only checked horizontal overflow and did not check whether elements were overlapping.

This taught me that being careful with my instructions can help prevent mistakes, but I still need to check the work myself. Tests only check what I tell them to check, so a green test suite does not always mean everything is correct.
