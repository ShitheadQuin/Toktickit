# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a Requester-facing ticketing application in which a Development Requester, selected
through a temporary testing mechanism, can create an IT support ticket with attachments, receive
a system-generated Ticket Number, and find, inspect and manage only their own tickets — on a
reusable Zen Green UI foundation that later sprints extend.

## 2. Stakeholder Request Interpretation

The IT department wants to start receiving real support requests, so this sprint delivers the
end-user half of the product: describe a problem, classify it, attach evidence, submit, then
locate and inspect the result. The system owns the Ticket Number and must guarantee a Requester
never sees another Requester's ticket.

Authentication arrives in Lab 3. Until then a Development Requester selector stands in for login
so that ownership behavior can be built and tested now. It is a testing mechanism and carries no
security guarantee.

The sprint also establishes the visual and component conventions later screens reuse, so the UI
work is a foundation rather than three isolated pages.

## 3. Scope

### Included
- Development Requester selection, current-Requester context, and Requester switching
- Create Ticket: form, validation, backend Ticket Number generation, success and failure states
- My Tickets: Requester-owned list with search, filtering, sorting and pagination
- Requester Ticket Detail: read-only view of one owned Ticket
- Attachment lifecycle: upload, metadata, download, soft removal
- Ownership protection enforced in the backend on every ticket and attachment operation
- Zen Green theme, reusable form/list/badge/validation/loading/empty/error components
- Responsive behavior at desktop, tablet and mobile

### Excluded
- Authentication and security: login, logout, passwords, hashing, sessions, tokens, authenticated
  identities, real role-based authorization
- IT Staff workflow: staff dashboard and queue, claiming or reassigning tickets, IT Priority
- Ticket collaboration: Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle after creation: any status change beyond the initial New
- Administration: managing users, Requesters, roles or reference data

## 4. Functional Requirements

- FR-01: The system shall load the list of active Development Requesters for selection.
- FR-02: The system shall let the user select a Development Requester as the current testing
  identity.
- FR-03: The system shall provide a Change Requester action, reloading all Requester-scoped data
  when the selection changes.
- FR-04: The system shall let the selected Requester submit a new Ticket with the required
  fields.
- FR-05: The backend shall generate a unique Ticket Number on successful Ticket creation.
- FR-06: The system shall list, in My Tickets, only Tickets owned by the current Requester.
- FR-07: My Tickets shall support keyword search over Ticket Summary and Ticket Number.
- FR-08: My Tickets shall support filtering by Category, Related System, Current Status and
  Requested Priority.
- FR-09: My Tickets shall support sorting by the defined sortable fields.
- FR-10: My Tickets shall paginate results according to the query contract in `api-spec.md`.
- FR-11: The system shall retrieve the detail of one Ticket owned by the current Requester.
- FR-12: The system shall reject retrieval of a Ticket not owned by the current Requester.
- FR-13: The system shall allow adding a permitted attachment to a Ticket the current Requester
  owns.
- FR-14: The system shall allow soft-removing an attachment the current Requester owns, with a
  reason.
- FR-15: The system shall block download and preview of a soft-removed attachment.
- FR-16: Every screen in scope shall present distinct loading, empty, no-results and error states
  as defined in `ui-spec.md`.
- FR-17: The system shall retrieve active Categories and active Related Systems for Ticket
  classification.

## 5. Business Rules

- BR-01: The official Ticket Number is generated by the backend and must be unique.
- BR-02: A new Ticket begins with Current Status New.
- BR-03: Lab 2 uses a Development Requester selector instead of login. The selected identity is
  for testing only and is not authentication.
- BR-04: Ticket Date is a server-generated timestamp captured at creation and is read-only.
- BR-05: A Ticket's owning Requester is fixed at creation and does not change afterward.
- BR-06: Only active Development Requesters may be selected; an inactive Requester cannot be
  chosen and cannot own new Tickets.
- BR-07: Switching the current Requester reloads all Requester-scoped screens for the new
  Requester; data is never merged between Requesters.
- BR-08: My Tickets and Ticket Detail return only data owned by the current Requester; no
  cross-Requester visibility is possible through any endpoint.
- BR-09: Ticket search matches Summary and Ticket Number, case-insensitive, partial match.
- BR-10: The default ticket-list sort is Ticket Date descending; Ticket Number descending is the
  secondary sort used to break ties.
- BR-11: Ticket Summary is required, trimmed, and must be 5-120 characters. Ticket Description is
  required, trimmed, and must be 10-2000 characters.
- BR-12: Category, Related System and Requested Priority are required and must reference active
  reference data.
- BR-13: The Submit button is disabled while a create-Ticket request is in flight, preventing
  duplicate submission.
- BR-14: If Ticket creation fails at the API, all entered field values remain in the form.
- BR-15: Attachments are limited to JPG, JPEG, PNG, WEBP and PDF, 5 MB maximum per file, 5 active
  attachments maximum per Ticket.
- BR-16: Attachment removal is soft. A removed attachment remains visible as metadata but cannot
  be downloaded or previewed.
- BR-17: Removing an attachment requires the Requester to confirm the action and provide a
  removal reason.
- BR-18: Only a Ticket's owning Requester may add or remove that Ticket's attachments; enforced
  in the backend.
- BR-19: If a Ticket is created successfully but an attachment upload fails, the Ticket is kept.
  The Requester is shown which attachment failed and may retry the attachment upload; Ticket
  creation is never rolled back for an attachment failure.
- BR-20: An inactive Requester's existing Tickets remain in the database but are not reachable
  through the Lab 2 selector.
- BR-21: An empty ticket list (a Requester with no Tickets) is shown distinctly from a no-results
  state produced by a search or filter.
- BR-22: Ticket Detail requests for a Ticket owned by another Requester, or for a Ticket that does
  not exist, return a safe not-found or forbidden response without revealing ticket data.
- BR-23: In Lab 3, the Development Requester selector is replaced by real authentication. The
  current Requester's identity will come from a verified session instead of manual selection;
  existing Ticket-Requester relationships from Lab 2 carry forward unchanged.
- BR-24: Uploaded files are stored under a server-generated unique filename. The Requester's
  original filename is retained only as display metadata, preventing path traversal or filename
  collisions.
- BR-25: Each attachment record stores original filename, stored filename, MIME type, size in
  bytes, uploaded timestamp, and, once removed, removed timestamp and removal reason.

## 6. UI Specification Summary

Full detail lives in `ui-spec.md`; this section summarizes intent per screen.

- **Application shell:** TokTickIT identity, My Tickets and Create Ticket navigation, current
  Requester display with a Change Requester action, active-page indication, responsive mobile
  navigation.
- **Development Requester Selection:** the only screen reachable with no Requester selected;
  dropdown of active Requesters, loading/empty/failure states, keyboard-accessible controls.
- **Create Ticket:** system-generated and read-only fields visually distinct from editable ones;
  Summary and Description given generous width; Attachments below the main fields; validation
  messages beside their field; busy Submit state; success state showing the generated Ticket
  Number.
- **My Tickets:** search, filters, sort, pagination, and a Create Ticket action; desktop table and
  mobile card representations; distinct loading, empty, no-results and failure states; Requested
  Priority and Current Status badges.
- **Requester Ticket Detail:** read-only Ticket fields grouped separately from the Attachment
  section; active, uploading, invalid, removed and unavailable attachment states.
- **Responsive rules:** desktop ≥ 992px multi-column, tablet 768-991px two-column, mobile
  <768px stacked with no horizontal scrolling, at every width no clipped labels or hidden buttons.

## 7. Data Changes

- **Requester** (Development Requester): id, name, email, `isActive`, timestamps. One Requester
  owns many Tickets.
- **Category:** id, unique name, `isActive`, timestamps (extends the existing Lab 1 model with
  `isActive`, since §6 requires retrieving only *active* Categories). One Category is used by
  many Tickets.
- **RelatedSystem:** id, unique name, `isActive`, timestamps. One Related System is used by many
  Tickets.
- **Ticket:** id, unique Ticket Number, `requesterId` (FK), `categoryId` (FK), `relatedSystemId`
  (FK), Summary, Description, Requested Priority, Current Status, timestamps. One Ticket belongs
  to one Requester and may have many Attachments.
- **Attachment:** id, `ticketId` (FK), original filename, stored filename, MIME type, size in
  bytes, uploaded timestamp, `isActive`, removed timestamp (nullable), removal reason (nullable).

Full field types, constraints, indexes and the migration are Issue #11's deliverable
(`server/prisma/schema.prisma`), built to this design.

## 8. API Contract

Full detail — request/response shapes, validation, pagination metadata, statuses and error cases
— lives in `api-spec.md`. Summary of the 10 required capabilities:

| Capability | Method & path |
|---|---|
| Retrieve active Categories | `GET /api/categories` |
| Retrieve active Related Systems | `GET /api/related-systems` |
| Retrieve active Development Requesters | `GET /api/requesters` |
| Create a Ticket | `POST /api/tickets` |
| Retrieve the selected Requester's Tickets | `GET /api/tickets` |
| Retrieve one owned Ticket | `GET /api/tickets/:id` |
| Upload an Attachment | `POST /api/tickets/:id/attachments` |
| Retrieve Attachment metadata | `GET /api/attachments/:id` |
| Download an active Attachment | `GET /api/attachments/:id/download` |
| Soft-remove an Attachment | `DELETE /api/attachments/:id` |

## 9. Acceptance Criteria

- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved
  and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts to open My Tickets,
  then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then
  the Ticket data is not returned.
- AC-04: Given the Development Requester list is loading, when the Selection screen is displayed,
  then a loading indicator is shown and the Continue button is disabled.
- AC-05: Given no active Development Requesters exist, when the Selection screen loads, then an
  empty state explains that no testing identities are available.
- AC-06: Given the Requester API call fails, when the Selection screen loads, then a safe error
  message is shown instead of a blank or crashed screen.
- AC-07: Given a Requester is selected and Continue is pressed, when the application shell
  renders, then the selected Requester's name is shown and a Change Requester action is
  available.
- AC-08: Given a Requester is already selected, when Change Requester is used to pick a different
  Requester, then every Requester-scoped screen reloads data for the new Requester.
- AC-09: Given the Create Ticket form is submitted with a missing required field, when validation
  runs, then a field-level message appears next to that field and no API call is made.
- AC-10: Given a Summary shorter than 5 or longer than 120 characters, when validation runs, then
  a field-level message appears and no API call is made.
- AC-11: Given the Submit button has been pressed, when the create-Ticket request is in flight,
  then Submit shows a busy state and is disabled.
- AC-12: Given the backend is unreachable during Ticket creation, when the Requester submits the
  form, then a safe error message is shown and all entered values remain in the form.
- AC-13: Given a Requester selects a file with a disallowed type or over 5 MB, when they attempt
  to attach it, then it is rejected with a clear message and never uploaded.
- AC-14: Given a Ticket already has 5 active attachments, when the Requester attempts to add a
  sixth, then the addition is rejected with a clear message.
- AC-15: Given Requester A is selected and has Tickets, when Requester B is selected instead,
  then Requester A's Tickets no longer appear in My Tickets.
- AC-16: Given a Requester has no Tickets, when they open My Tickets, then an empty state
  distinct from a no-results state is shown.
- AC-17: Given a search matches no Ticket, when the search runs, then a no-results state is shown.
- AC-18: Given more Tickets exist than fit on one page, when My Tickets loads, then pagination
  controls navigate to subsequent pages and show the correct subset.
- AC-19: Given a sort option is selected, when the list reloads, then Tickets are ordered by the
  selected field.
- AC-20: Given a filter is applied, when the list reloads, then only matching Tickets are shown.
- AC-21: Given a Requester opens Ticket Detail for their own Ticket, when the screen loads, then
  all Ticket fields are shown read-only.
- AC-22: Given a Requester adds a permitted attachment to their own Ticket, when the upload
  succeeds, then it appears in the active attachment list.
- AC-23: Given a Requester soft-removes their own attachment with a reason, when the removal
  succeeds, then it is shown as removed metadata and its download and preview are blocked.
- AC-24: Given a removed attachment, when a download is attempted directly, then the request is
  rejected rather than returning the file.
- AC-25: Given Create Ticket, My Tickets, or Ticket Detail is viewed at desktop, tablet, or mobile
  width, when the layout renders, then no clipped labels, overlapping messages, hidden buttons,
  or unintended horizontal scrolling occur.
- AC-26: Given the Development Requester Selection screen, when navigated using only the
  keyboard, then every control is reachable and usable without a mouse.
- AC-27: Given a Requester is selected, when the Create Ticket screen loads, then the
  Requester field displays the selected Requester's name, and on successful submission the saved
  Ticket's `requesterId` matches the selected Requester.

## 11. Assumptions and Decisions

- **Ticket Number format:** `TKT-<year>-<6-digit sequence>` (e.g. `TKT-2026-000001`), generated
  by the backend from a database sequence. Chosen for readability and sortability; satisfies
  BR-01's uniqueness requirement. The sequence number doesn't need to equal the database id —
  `api-spec.md`'s example simply shows both for a freshly-seeded database where they happen to
  coincide.
- **Summary/Description limits:** Summary 5-120 characters, Description 10-2000 characters, both
  required and trimmed. Summary is kept short so it fits a list row without wrapping; Description
  is bounded generously enough for real detail while protecting the UI layout and database column.
- **Requested Priority values:** LOW, MEDIUM, HIGH. Lab 2 only requires Requested Priority — IT
  Priority belongs to a later lab's IT Staff workflow — so a simple three-level scale was used
  rather than importing a heavier scheme this sprint does not need.
- **Ticket-list page size:** default 10, permitted sizes 5, 10, 20. The smallest permitted size
  makes pagination demonstrable with a small number of tickets rather than requiring dozens to be
  created by hand.
- **`Category` gains `isActive`:** the Lab 1 model has no active flag, but §6 requires retrieving
  only active Categories. The field is added rather than assuming all Lab 1 categories are active
  by omission, so a Category could be retired without deleting its history.
